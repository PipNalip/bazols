# Bazols Reporting MVP — Feature Spec

**Статус:** утверждено к локальной реализации 2026-09-15; Production delivery остаётся отдельным backlog/gate
**Источник требований:** `docs/specs/bazols-reporting-discovery.md`

**Статус Phase 3 на 2026-09-16:** локально реализованы REQ-007, REQ-008, manager-часть REQ-009/010 и AC-11/12: Reports API, React/MUI shell, login/session/logout, выбор ресторана и периода, обе таблицы и обязательные состояния. Browser-сценарий использует реальные NestJS, Vite и PostgreSQL entry points с синтетической fixture. Admin React-экраны из пунктов 4–5 REQ-009 и полный fake-source/worker сценарий AC-14 остаются следующей фазой; Production activation не выполнялась.

## 1. Цель

Создать внутреннее веб-приложение Bazols, в котором менеджеры видят рейтинги сотрудников и товаров по данным разрешённого внутреннего API ресторанной системы, а администратор вручную запускает безопасную read-only синхронизацию.

## 2. Пользователи и роли

### Администратор

- входит по собственному логину и паролю;
- создаёт и блокирует менеджеров;
- сбрасывает менеджеру пароль;
- назначает менеджеру доступные рестораны;
- вручную запускает синхронизацию ресторана за выбранный период;
- видит журнал синхронизаций.

### Менеджер

- входит по собственному логину и паролю;
- видит только назначенные ему рестораны;
- выбирает ресторан и период;
- просматривает рейтинги сотрудников и товаров;
- видит время последней успешной синхронизации;
- не запускает синхронизацию и не управляет пользователями.

Саморегистрация и восстановление доступа по email в MVP отсутствуют.

## 3. Подтверждённые свойства источника

Read-only исследование 2026-09-15 подтвердило:

- исходный интерфейс реализован на React и использует внутренние JSON-endpoints;
- авторизация выполняется через `Authenticate`, затем `GetPermissions` и `SetRole`;
- `Reports/EmployeesRating/GetData` принимает `beginDate`, `endDate`, `employeeType`, `employeeSurname`, `page`, `pageSize`;
- проверка 30-дневного периода вернула 13 сотрудников, 151 уникальный заказ и 986 уникальных позиций;
- `order.items[].priceWithDiscountForOrder.value` суммируется в `order.price.value` для всех 151 проверенного заказа;
- отдельного поля количества в позиции нет: одна уникальная запись `item` считается одной проданной единицей;
- ответ содержит персональные данные сотрудников и клиентов;
- доступ к себестоимости и техническим картам пока не подтверждён.

Эти наблюдения являются текущим контрактом адаптера, а не обещанием владельца источника. Изменение контракта должно приводить к безопасному отказу нормализации, а не к записи неверных расчётов; зашифрованный исходный response body при этом сохраняется для диагностики.

## 4. Технологическое решение

- Node.js 22+ и TypeScript;
- npm workspaces;
- NestJS REST API;
- отдельный Node.js worker без автоматического расписания;
- PostgreSQL;
- Prisma ORM и миграции;
- React + Vite;
- MUI Core;
- только MIT-лицензированный MUI X Data Grid Community при необходимости;
- Recharts для графиков;
- Vitest для unit-тестов;
- Supertest для API integration-тестов;
- Playwright для browser smoke/E2E и исследования источника;
- Tailwind CSS не используется.

## 5. Архитектура

```text
React web
   │ secure session cookie
   ▼
NestJS API ───────────────► PostgreSQL
   │                           ▲
   │ creates queued SyncRun    │ claims job, writes snapshot + normalized rows
   ▼                           │
Manual sync request       Node.js worker
                               │ allowlisted GET only
                               ▼
                     Internal source API
```

API не выполняет долгую синхронизацию внутри HTTP-запроса. Оно создаёт запись `SyncRun` со статусом `queued`. Worker забирает задания из PostgreSQL. Redis и внешний брокер очередей в MVP не нужны.

### 4.1. Контракт API и процессов этапа синхронизации

| Поверхность | Доступ | Назначение |
|---|---|---|
| `POST /api/auth/login` | same-origin, rate-limited | Создать server-side session и вернуть CSRF token |
| `GET /api/auth/me` / `POST /api/auth/logout` | authenticated; logout также CSRF | Восстановить frontend auth state / отозвать session |
| `POST /api/sync-runs` | ADMIN + Origin + CSRF | Создать `queued` запуск; конфликт при другом active run ресторана |
| `GET /api/sync-runs`, `GET /api/sync-runs/:id` | ADMIN | Читать status, counters и только безопасный error code |
| `GET /api/source-discovery` | ADMIN | Прочитать только source unit IDs и roles |
| `/api/restaurants*`, `/api/users*` | authenticated; mutations ADMIN + Origin + CSRF | Mapping ресторанов и lifecycle менеджеров |
| `npm run start:worker --workspace @bazols/api` | отдельный процесс | Claim, heartbeat, import и terminal state/audit |

Opaque session token существует только в cookie клиента; PostgreSQL хранит его HMAC-SHA256 hash. Cookie имеет `HttpOnly`, `SameSite=Lax`, а в Production также `Secure`. CSRF token детерминированно выводится через HMAC из opaque session token и сравнивается constant-time. Блокировка или reset пароля отзывают активные sessions пользователя.

Queue claim выполняется guarded state transition `QUEUED → RUNNING`; partial unique index разрешает не более одного `QUEUED/RUNNING` запуска на ресторан. Worker не имеет duration timeout: во время активной работы он обновляет heartbeat, а отсутствие heartbeat более 15 минут переводит запуск в `FAILED`. Terminal state и соответствующий safe audit event записываются одной транзакцией.

## 6. Требования

### REQ-001 — авторизация приложения

- Пользователи входят по логину и паролю Bazols, не по реквизитам исходного сайта.
- Пароль хранится только как Argon2id-хеш.
- Успешный вход создаёт серверную сессию.
- В браузер передаётся непрозрачный идентификатор сессии в cookie `HttpOnly`, `SameSite=Lax`; `Secure` обязателен в production, а локальный HTTP-режим разрешает его отключение только в development/test.
- Состояние сессии хранится в PostgreSQL; выход и блокировка пользователя отзывают сессию.
- State-changing запросы проверяют same-origin `Origin` и CSRF-защиту.

### REQ-002 — разграничение ресторанов

- Связь менеджера и ресторана хранится в `UserRestaurant`.
- Каждый запрос отчёта проверяет доступ на сервере.
- Администратор имеет доступ ко всем ресторанам.
- Подмена restaurant ID должна возвращать `403` без утечки существования чужих данных.

### REQ-003 — read-only source connector

Разрешённые операции MVP:

- `GET /Infrastructure/Authenticate/Authenticate`;
- `GET /Infrastructure/Authenticate/GetPermissions`;
- `GET /Infrastructure/Authenticate/SetRole`;
- `GET /Reports/EmployeesRating/GetData`.

Коннектор:

- использует HTTPS и блокирует все redirect, включая same-origin;
- не принимает произвольный URL или метод от вызывающего кода;
- запрещает `POST`, `PUT`, `PATCH`, `DELETE`;
- запрещает неизвестный endpoint;
- не логирует query string, пароль, cookies, токены и response body;
- держит cookies только в памяти одного запуска;
- проверяет `isSuccess`, структуру payload и денежные инварианты;
- прекращает импорт при изменении обязательной структуры.

### REQ-004 — ручная синхронизация

- До первой синхронизации администратор запускает read-only обнаружение доступных подразделений и ролей, затем создаёт связь ресторана с явными `sourceUnitId`, `sourceRole` и timezone.
- Только администратор создаёт синхронизацию, выбрав ресторан, начальную и конечную даты.
- Период не может быть пустым, обратным или уходить в будущее.
- Для одного ресторана одновременно существует не более одной активной синхронизации.
- Статусы: `queued`, `running`, `succeeded`, `failed`.
- Worker постранично загружает весь отчёт до `totalRows`.
- Ошибка или пустой ответ не удаляют последний успешный набор данных.
- Все нормализованные изменения одного запуска, включая reconciliation и счётчики, фиксируются одной транзакцией; ошибка любой страницы откатывает весь нормализованный run.
- Повторный импорт того же периода не создаёт дубликаты заказов и позиций.
- После полного непустого успешного импорта записи указанного ресторана и периода, которые больше не присутствуют в источнике, исключаются из текущих отчётов, но остаются восстановимыми из зашифрованных снимков.
- Если worker завершился аварийно, зависший `running`-запуск обнаруживается по heartbeat и переводится в `failed` с безопасным кодом до разрешения нового запуска.

### REQ-005 — полное хранение ответа

- Каждый успешно полученный отчётный response body сохраняется полностью в `RawSnapshot` как исходные байты до парсинга и нормализации.
- Невалидный отчётный response body также сохраняется до contract validation, но не изменяет нормализованные данные.
- Response body шифруется приложением через AES-256-GCM до записи в PostgreSQL.
- Ключ шифрования приходит только из `RAW_DATA_ENCRYPTION_KEY` окружения и не хранится в БД или Git.
- Сохраняются ciphertext, IV, authentication tag, версия формата, endpoint, ресторан, период, номер страницы, content type и время получения.
- Пароли, cookies, токены и HTTP authorization headers не входят в snapshot.
- Snapshot не выдаётся менеджерам и не отправляется во frontend в MVP.
- Снимки и нормализованные данные хранятся бессрочно до отдельного согласованного удаления.

### REQ-006 — нормализация

Минимальные сущности:

- `User`, `Session`, `Restaurant` с `sourceUnitId`, `sourceRole` и timezone, `UserRestaurant`;
- `SyncRun`, `RawSnapshot`;
- `Employee`, `Order`, `Product`, `OrderItem`.

Идемпотентность обеспечивают уникальные пары `(restaurantId, sourceId)` для сотрудников, заказов, продуктов и позиций. Дубликаты employee/order/item ID и конфликтующие product ID между страницами отклоняются до записи. Заказы и позиции хранят признак актуальности/последний успешный sync для безопасной сверки повторно загруженного периода; границы периода рассчитываются в IANA timezone ресторана. Денежные значения хранятся как PostgreSQL `numeric`, не как binary float.

### REQ-007 — рейтинг сотрудников

Для выбранных ресторана и периода:

- `revenue` = сумма `order.price.value` по уникальным заказам сотрудника;
- `ordersCount` = количество уникальных заказов сотрудника;
- `averageCheque` = `revenue / ordersCount`, либо `0` при отсутствии заказов;
- пользователь переключает сортировку между выручкой, количеством заказов и средним чеком;
- сортировка по убыванию, затем стабильный tie-break по отображаемому имени и source ID;
- API возвращает место, ID, имя, три метрики и валюту.

### REQ-008 — рейтинг товаров

Для выбранных ресторана и периода:

- `unitsSold` = количество уникальных `OrderItem` продукта;
- `revenue` = сумма `orderItem.priceWithDiscountForOrder.value`;
- пользователь переключает сортировку между количеством и выручкой;
- сортировка по убыванию, затем стабильный tie-break по названию и source ID;
- API возвращает место, ID, название, обе метрики и валюту.

### REQ-009 — интерфейс

Обязательные экраны:

1. вход;
2. общий экран рейтингов с вкладками «Сотрудники» и «Товары»;
3. верхняя операционная лента: ресторан, период, последняя успешная синхронизация;
4. администрирование менеджеров и назначений ресторанов;
5. ручной запуск и журнал синхронизаций.

Состояния интерфейса:

- загрузка;
- данные загружены;
- доступных ресторанов нет;
- данных за период нет;
- синхронизация выполняется;
- последняя синхронизация завершилась ошибкой;
- сессия истекла;
- доступ запрещён.

### REQ-010 — визуальный контракт

- Текстовый знак `Bazols`, без графической эмблемы.
- Спокойная светлая тема: тёплый белый фон, нейтрально-зелёные поверхности, тёмно-зелёный текст, шалфейный основной цвет и ограниченный медный акцент.
- Никаких Tailwind, ярких градиентов, glassmorphism и постоянной декоративной анимации.
- Интерфейс работает с клавиатуры, имеет видимый focus и не передаёт статус только цветом.
- Desktop — основной рабочий формат; интерфейс остаётся usable на планшете и телефоне.

### REQ-011 — аудит и безопасные ошибки

- Журналируются вход, выход, создание/блокировка пользователя, изменение назначений ресторанов, запуск и результат синхронизации.
- Логи содержат event type, actor ID, restaurant ID, sync ID, timestamp и безопасный error code.
- Логи не содержат пароль, cookie, токен, полный URL с query, response body и персональные значения payload.
- Пользователь получает понятное сообщение и correlation ID; внутренний stack trace остаётся только в server logs без чувствительного payload.

## 7. Acceptance criteria

### AC-01 — read-only boundary

Автоматический тест доказывает, что source connector выполняет только четыре allowlisted GET-операции; неизвестный путь, cross-origin redirect и методы `POST`, `PUT`, `PATCH`, `DELETE` отклоняются до сетевого вызова.

### AC-02 — безопасная авторизация источника

При успешном fake-source сценарии connector выполняет authenticate → permissions → set role → report, не сохраняет cookies на диск и не передаёт секреты logger-у. Неверные реквизиты завершают sync как `failed`, не создавая нормализованных строк.

### AC-03 — контракт payload

Fixture, повторяющий подтверждённую структуру источника, успешно валидируется. Удаление обязательного ID, цены или массива items вызывает fail-closed ошибку контракта, сохраняет только зашифрованный исходный response body и не изменяет последний успешный нормализованный набор данных.

### AC-04 — шифрование полного ответа

В БД отсутствует открытый JSON payload. Расшифровка правильным ключом возвращает байт-в-байт исходный HTTP response body; неверный ключ или изменённый ciphertext завершаются ошибкой аутентификации.

### AC-05 — идемпотентность

Два последовательных импорта одной fixture создают одинаковые количества сотрудников, заказов, продуктов и позиций; второй импорт не создаёт дубликаты.

### AC-06 — employee formulas

На фиксированной fixture тест подтверждает сумму уникальных заказов, количество заказов, средний чек, округление денег и стабильный порядок при равных значениях.

### AC-07 — product formulas

На фиксированной fixture тест подтверждает, что одна запись item равна одной единице, а выручка считается из `priceWithDiscountForOrder.value`, а не из `price` или `productPrice`.

### AC-08 — restaurant isolation

Менеджер ресторана A получает `200` для A и `403` для B через реальный API guard. Подмена route/query/body не обходит проверку. Администратор получает доступ к обоим.

### AC-09 — user lifecycle

Администратор создаёт менеджера и назначает ресторан; менеджер входит, видит только назначение и теряет доступ после блокировки или удаления назначения. Неадминистратор не может создать пользователя или запустить sync.

### AC-10 — sync lifecycle

Запуск возвращает `202` и `queued`; worker переводит запись в `running`, затем `succeeded` либо `failed`. Второй активный запуск для того же ресторана отклоняется конфликтом. Ошибка источника сохраняет предыдущие отчётные данные. Зависший `running`-запуск восстанавливается в `failed` по heartbeat.

### AC-11 — report UI

Browser-тест проходит login → выбор ресторана/периода → обе вкладки → переключение метрики и проверяет, что строки меняют стабильный порядок согласно API.

### AC-12 — UI states and accessibility

Компонентные/browser-тесты покрывают loading, empty, error, forbidden и expired-session состояния; основные controls доступны по keyboard и имеют доступные имена.

### AC-13 — secret and PII logging guard

Тест с sentinel-значениями в логине, cookie, клиентском телефоне и payload подтверждает, что ни одно sentinel-значение не появляется в собранных логах или HTTP error responses.

### AC-14 — real entry point

На чистой локальной PostgreSQL приложение запускается документированной командой; администратор входит, запускает sync против локального fake source, worker импортирует fixture, а React показывает оба рейтинга.

## 8. Не входит в MVP

- автоматическая синхронизация по расписанию;
- себестоимость, маржинальный результат и технические карты;
- уведомления об изменении цены;
- Telegram-бот;
- email-восстановление пароля;
- самостоятельная регистрация;
- экспорт CSV/Excel;
- просмотр и расшифровка полного snapshot через frontend;
- автоматическое удаление данных;
- реализация и активация CI/CD, hosting и Production deployment; они спроектированы отдельно в `docs/specs/bazols-delivery.md` и имеют собственные approval gates.

## 9. Риски и решения

| Риск | Решение MVP |
|---|---|
| Недокументированный API изменится | Runtime schema validation, contract fixtures, fail closed |
| Источник передаёт пароль через GET | Не логировать URL/query, только HTTPS, краткоживущая memory-only cookie jar |
| Источник возвращает лишние персональные данные | Зашифрованный snapshot, закрытый frontend-доступ, RBAC и audit |
| Бессрочное хранение увеличивает объём и последствия утечки | Шифрование payload, резервные копии с тем же уровнем защиты, отдельная будущая процедура удаления |
| Двойной запуск создаст гонку | DB uniqueness/locking для активного SyncRun на ресторан |
| Повторный период задублирует данные | Upsert по `(restaurantId, sourceId)` и integration-тест повторного импорта |
| Источник недоступен | `failed` sync без удаления последнего успешного набора |

## 10. Решения, отложенные до следующих фаз

- endpoint и формула себестоимости;
- цена, которую считать базовой для price-change уведомления;
- канал уведомлений;
- срок и процедура удаления данных;
- точные Production activation inputs (domain/DNS, deploy owner, SSH identity, backup destination/retention и repository/package visibility) согласно `docs/specs/bazols-delivery.md`;
- операционный список отложенных Production-задач ведётся в `docs/backlog.md`.
