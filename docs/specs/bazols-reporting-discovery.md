# Bazols Reporting — исследование продукта

**Статус:** черновик, основные продуктовые решения приняты; модель входа и детали отчётов ещё уточняются

## Цель

Создать внутреннюю систему отчётности для персонала ресторанов Bazols на основе данных из внешнего веб-сайта, у которого нет доступного публичного API или прямого доступа к базе данных.

## Исходные ограничения

- Внешний сайт использует обычный логин и пароль.
- Интеграция должна работать только на чтение и не изменять данные источника.
- Реальные реквизиты доступа хранятся только в локальном `.env` и не входят в Git.
- До реализации требуется проверить, существует ли внутренний JSON/API-трафик, который использует сам веб-интерфейс.
- Основной пользовательский интерфейс — веб-приложение на React с MUI Core и, при необходимости, только MIT-лицензированными компонентами MUI X Community.
- Tailwind CSS и коммерческие компоненты MUI X Pro/Premium в MVP не используются.
- Telegram рассматривается только как дополнительный канал уведомлений и коротких сводок.
- Первый релиз предназначен для нескольких менеджеров; каждый менеджер видит только назначенные ему рестораны.

## Первые пожелания заказчика

1. Два отдельных рейтинга: сотрудников по их продажам и товаров/блюд по продажам.
2. Если источник содержит себестоимость, показывать:
   - сумму продаж;
   - суммарную себестоимость проданных позиций;
   - разницу между продажами и себестоимостью.
3. Использовать доступные в источнике карточки продуктов и сведения о себестоимости.
4. Уведомлять о повышении или снижении цены продукта.

## Предварительные продуктовые сценарии

### Сценарий 1: рейтинг продаж

Менеджер выбирает доступный ему ресторан и период, после чего отдельно видит рейтинг сотрудников и рейтинг товаров/блюд по выбранному показателю продаж.

Рейтинг сотрудников переключается между:

- выручкой;
- количеством заказов;
- средним чеком.

Рейтинг товаров/блюд переключается между:

- количеством проданных единиц;
- выручкой.

При переключении показателя таблица пересортировывается по убыванию и показывает место, название, значение показателя и данные, необходимые для понимания расчёта.

### Сценарий 2: оценка разницы между продажами и себестоимостью

Если источник предоставляет достаточные данные, пользователь видит продажи, себестоимость и вычисленную разницу. Этот показатель нельзя называть чистой прибылью без учёта остальных расходов ресторана.

### Сценарий 3: изменение цены

После очередной успешной синхронизации система сравнивает цену продукта с предыдущим сохранённым значением и фиксирует повышение или снижение.

## Предварительное техническое направление

Система разделяется на четыре области:

1. коннектор к внешнему сайту;
2. нормализованное хранилище и история синхронизаций;
3. серверное API и расчёт отчётов;
4. веб-интерфейс, не зависящий от устройства сбора данных.

Предварительно выбран TypeScript-стек: React, NestJS, PostgreSQL, Prisma и отдельный Node.js-коннектор. Коннектор использует внутренний JSON API источника; Playwright нужен для исследования сетевых запросов и как запасной вариант, но не как основной механизм регулярной синхронизации.

## Результаты исследования источника

- React-клиент источника использует внутренние JSON-endpoints.
- Авторизация состоит из входа, получения permissions и выбора активных подразделения и роли.
- `EmployeesRating/GetData` предоставляет сотрудников, связанные заказы, проданные позиции и цены.
- Одну загрузку можно нормализовать в два отчёта: рейтинг сотрудников и рейтинг товаров.
- Найдены также операции изменения данных. Коннектор должен работать по закрытому allowlist разрешённых GET-endpoints; неизвестные endpoints и операции `Save`, `Edit`, `Remove`, `Delete`, `Add` и `Cancel` блокируются.
- Доступ к себестоимости и техническим картам пока не подтверждён.

## Хранение данных

- Система сохраняет полный ответ разрешённого API как зашифрованный исходный снимок.
- Пароли, cookies, токены и заголовки авторизации не являются отчётными данными и никогда не сохраняются.
- Для отчётов отдельно ведутся нормализованные таблицы сотрудников, продуктов, заказов, позиций, цен и синхронизаций.
- Исходный снимок не отправляется напрямую в браузер и не попадает в прикладные логи.
- Права исходной учётной записи ограничивают новые загрузки, но не управляют уже скопированными данными. Доступ к сохранённым данным контролирует собственная ролевая модель приложения.
- Полные исходные снимки и нормализованные данные хранятся бессрочно, пока администратор явно не запустит согласованное удаление.
- Отзыв permissions на стороне источника прекращает новые загрузки, но сам по себе не удаляет ранее сохранённые данные.

## Frontend

- React и TypeScript собираются через Vite.
- Базовые элементы интерфейса, формы, диалоги, фильтры и адаптивная сетка строятся на MUI Core.
- Для таблиц допустим только бесплатный MUI X Data Grid Community; функциональность, требующая Pro/Premium-лицензии, не входит в MVP.
- Tailwind CSS не устанавливается.
- Визуальная тема задаётся собственными design tokens Bazols: цветами, типографикой, плотностью таблиц, состояниями и адаптивными размерами.
- Доступность включает управление с клавиатуры, видимый focus, подписи элементов управления и достаточный контраст.

### Визуальное направление

- Логотип — текстовый знак `Bazols`, без отдельной графической эмблемы.
- Характер интерфейса — спокойный, собранный и пригодный для длительной работы с отчётами.
- Базовая палитра: тёплый почти белый фон, светлая нейтрально-зелёная поверхность, тёмно-зелёный основной текст, приглушённый шалфейный основной цвет и ограниченный медный акцент.
- Красный и зелёный статусы не используются как единственный способ передать значение: рядом всегда есть текст или символ.
- Таблицы остаются достаточно плотными для аналитики, но сохраняют заметные заголовки, разделители групп и удобные области нажатия.
- Скругления умеренные; яркие градиенты, декоративное стекло, тяжёлые тени и постоянная анимация не используются.
- Ключевой визуальный приём — единая спокойная «операционная лента» с выбранным рестораном, периодом и временем последнего обновления над обоими рейтингами.

## Доступ менеджеров

- Саморегистрация в MVP отсутствует.
- Администратор создаёт менеджеров с логином и временным паролем, сбрасывает пароль и назначает доступные рестораны.
- Восстановление пароля по email и вход через Telegram в MVP отсутствуют.
- После входа NestJS создаёт серверную сессию; идентификатор сессии передаётся только в cookie с `HttpOnly`, `Secure` и `SameSite`.
- Пароли хранятся только как стойкие хеши; исходный пароль менеджера не сохраняется и не журналируется.
- Каждый запрос отчёта проверяет назначение менеджера на ресторан на стороне NestJS API; фильтра frontend недостаточно.
- Менеджер не может получить данные другого ресторана подменой URL, query-параметра или API-запроса.
- Изменения назначений и обращения к полным исходным снимкам журналируются.

## Запуск синхронизации в MVP

- Синхронизацию вручную запускает только администратор нашего приложения.
- Автоматический планировщик в MVP отсутствует.
- Перед запуском администратор выбирает ресторан и период загрузки.
- Для одного ресторана одновременно может выполняться только одна синхронизация.
- Повторный импорт тех же исходных заказов и позиций не создаёт дубликаты.
- Ошибка или пустой ответ не удаляют последний успешный набор данных.
- Менеджер видит время последней успешной синхронизации, но не может запускать её самостоятельно.

## Безопасность

- Предпочтительна отдельная учётная запись источника с минимальными правами.
- Пароли, cookies и browser storage не должны попадать в Git, логи, отчёты об ошибках или снимки HTML.
- Авторизация может выполнять необходимый запрос входа, но сборщик не должен отправлять прикладные запросы изменения данных.
- Неудачная или пустая синхронизация не должна удалять последний корректный снимок.
- Каждая синхронизация должна иметь время, статус и безопасное диагностическое сообщение.

## Открытые вопросы

- Как заказчик хочет получать уведомления об изменении цены?
- Есть ли у источника CAPTCHA, двухфакторная авторизация или ограничение автоматизированного доступа?
- Разрешает ли владелец исходного сайта такую автоматизацию?

## Пока не входит в MVP

- изменение данных на исходном сайте;
- полноценный Telegram-интерфейс отчётности;
- прогнозирование и AI-рекомендации;
- бухгалтерский расчёт чистой прибыли;
- реализация и активация deployment/CI/CD; их отдельная архитектура описана в `docs/specs/bazols-delivery.md`, а внешние изменения требуют собственных подтверждений.
